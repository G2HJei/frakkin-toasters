What to watch
1. The view needs to be airtight. Several components hand out writable internals today, and some can be changed without even a cast:                    SpaceLocationsBoard.shipsInSpace() returns the board's own mult methods that write through it.
- Lombok @Getter exposes raw collections: the piles in SkillCheckHolder, Player.revealedCivilianShips() and Game.removedComponents(). Declaring them as List in an interface doesn't help, because List has add.
- Getters return writable objects: every Deck (player hands and DecksHolder), Player, ships with setters (HumanFighter.pilot(Character),
  Basestar.damage(...)), and Game.die().

Fixes:
- Have components return copies or view types, and give each kind of write its own method.
- Return snapshots (List.copyOf, stream .toList()), not live rr can then loop over ships while a mutator moves them.AdvancePursuitTrackEventProcessor already copies the map with new HashMap<>(...) for that reason.
- As a catch-all, tag the write methods (e.g. @Mutates) and adnt.. never calls them. That also catches a processor casting the view back to the real class.

2. Give processors the mutators only for process(). Pass them as a parameter, or set the field in the base class just before calling process(). Then init()
and isValid() can't change state.

3. The methods you're keeping have hidden side effects. A mutadid, so a component method that does more than its name saysleaves gaps in the log:
- Deck.draw() reshuffles the discard pile when the deck runs ow X" but never "Politics deck reshuffled".
- Game.damage(location) also sends everyone in that location to Sickbay.
- Game.destroy(basestar) discards its damage cards and returnships.returned() clears the damage.

Make component methods do one thing, or report what else they ch step and logs the ones that matter.

4. Rules that keep mutators trustworthy:
- One call is one fact, at the level a player would say out loud ("P1 drew 2 Politics cards"). Your draw-to-hand example is exactly that level.
- Log after the change succeeds, using the same values that ma
- Build bigger operations from smaller mutators instead of going around them. For example, damageLocation calls moveCharacter for each character there, so
  the Sickbay moves are logged as their own facts under it.
- Always log, instead of "when needed". Describers decide what to show and can return nothing for bookkeeping facts. A complete log can later drive replay,
  reconnects or client sync, and it keeps mutator tests unifor
- Log the full data, such as the actual cards drawn. Hiding things from other players is the describers' job.
- Mutators do mechanics, not decisions. Picking targets, "destr movement stay in processors. Consequences that always comewith an operation belong in the mutator, like Sickbay on location damage or a reshuffle when a deck runs out.
- Return immutable values or view types (drawn cards, ship ids
- Mutators shouldn't take an event parameter for logging. The engine opens the journal scope, and mutators just append to it.

5. Only mutators should write, the engine included. Component write methods stay public, so anything holding a Game could change it without logging. That
includes the future engine advancing step or currentPlayer, anit rule, allowing only ..mutator.. and tests to call @Mutatesmethods, keeps the log complete.

6. Tests:
- Mutator tests check the state change and the logged fact.
- Processor tests use real mutators and assert the logged facts and the followup. Don't mock the mutators: a mock changes nothing, so a processor that
  reads its own changes would see stale state.
- Test setup can keep using the concrete classes directly, without logging. Clear the journal before execute.

7. If you want replay later: have each mutator build its fact and apply it through a single apply(fact). Replay then reuses the same code instead of
needing a second implementation. You don't need this now.

- Mutator matches your "mutate path" and pairs clearly with Garawbacks: in Java "mutator" often means a setter, and rollDie()or "P1 looked at the top crisis card" don't change any state.
- GameOperations is more accurate if one object holds everythi. For precedent: Forge, the open-source Magic: The Gatheringengine, is built along similar lines. Its rules code calls a GameAction class to move cards, and a log formatter turns the resulting events into log    lines. I wouldn't use "Action" here, because it clashes withctionEvent.
